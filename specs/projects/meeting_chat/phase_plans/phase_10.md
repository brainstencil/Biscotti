# Phase 10: Hardware validation in Biscotti Dev

## Overview

Validates meeting chat on this Mac in Biscotti Dev (`DerivedData/Development-meeting-chat`, Apple Development signed, with its own runtime folder `runtime-meeting-chat` from 01:39 on 29 October; see step 4), fixes what the checks find, and records the results in the checklist below. The agent drives Biscotti Dev with the background computer-use tools (`app_*`), saves the screenshot that shows each result under `demo/meeting-chat/phase10/` (named by check ID, outside the repo), and reads the unified log for `net.scosman.biscotti`.

The manager's brief (`.specs_skill_state/phase10-brief.md`) splits the work:

- **Part A (no recording):** every check on saved meetings, keyboard use, ⌘J, quitting mid-answer, and the visual review of the meeting page in light and dark mode. The development store holds the phase 6 meetings, with final transcripts.
- **Part B (recording, once the user has granted microphone and system audio to the signed build):** asking during a recording with the live transcript on and off, time chips and "Back to chat" on the recording screen, Turn On from the field, Stop mid-answer during a recording, and the card after Stop. A fixture plays through the speakers with `afplay` (`live_bench/fixtures/soak/mixed.wav`).

Dark mode uses a launch argument (`--args -AppleInterfaceStyle Dark`), never the system setting. Checks that need a system setting or full-screen control are the user's, listed as "user", not failed.

## Steps

1. **Time chip with the live transcript off** (`RecordingUI/RecordingViewModel+Chat.swift`, carried item 1). `showTranscript(at:)` starts with `guard showsLiveTranscript else { return }`: with no drawer to open, the card stays open, and no stale "Back to chat" or expanded-drawer flag is left behind.
2. **Return during an input-method composition** (`MeetingChatUI/ChatQuestionField.swift`). `ChatReturnKey.action(modifiers:isComposing:)` returns `.send`, `.lineBreak` or `.compose`. `handleReturn` reads `ChatReturnKey.isComposingInKeyWindow` (the key window's first responder, as an `NSTextInputClient`, has marked text) and returns `.ignored` for `.compose`, so the input method confirms its composition and nothing is sent. `.onSubmit` is not reached by a composition's Return.
3. **The chat list follows a thread that outgrows the card** (`MeetingChatUI/ChatMessageList.swift`, check A13). The list stopped following when its offset moved up while it was not at the end, and it read that as the user scrolling up. A thread whose first answer fits the card sits at the card's bottom; the next question makes the content outgrow the card, the scroll view moves the offset up, and the list stopped following, so the answer streamed out of view under the down-arrow button. `ScrollPlace` now carries the content and container heights. `follows(after:wasFollowing:)` keeps following through an upward offset change only where the scroll view makes it: the content fitted the card before, or the card changed height. In a list that already scrolls, new text below the end does not move the offset, so an offset more than 1 pt up is the user's, even when the same update carries new text or a newly measured row. `needsScrollToEnd(after:isFollowing:)` scrolls to the end again when the content or the card changed height and the end left the view while the list follows (a row measured after the last scroll).
4. **A runtime folder per development build** (`Tools/development.sh`, in its own commit, apart from the chat work). The optional `BISCOTTI_DEV_RUNTIME_ROOT` (default `$BUILD_ROOT/runtime`; a trailing slash is dropped and a relative path is refused before any build) sets `RUNTIME_ROOT`, the existing-root check and the bundle check (`verify_development_bundle.py` already takes the root as its argument), and passes `BISCOTTI_DEVELOPMENT_ROOT=<root>` to xcodebuild, so the app and both XPC services carry it in `BiscottiDevelopmentRoot`. `specs/projects/development_isolation/usage.md` describes both overrides. Reason: another session's Biscotti Dev from `DerivedData/Development`, whose data model has no chat entities, opened the shared `runtime` store and removed the chat tables each time it started. This phase's build now uses `runtime-meeting-chat`, an APFS clone of `runtime` made at 01:39 (`cp -cR`, with both SQLite databases replaced by `.backup` snapshots because that other build was running, idle).
5. **Defects the checks find:** fixed here when they are in this project's code and the fix is small and clear, each with a test; otherwise recorded in the table for the manager.

Beside the text, the count narrowed the vertical text field without the field wrapping its lines again. Layout only; checked in the app, no unit test.

7. **Things drawn outside their view by an alignment guide in an overlay** (from the manager's full-screen round). Both placed a view outside its parent with `.alignmentGuide` inside `.overlay(alignment:)`, and the guide was ignored:
   - `TranscriptUI/TranscriptItemRow.swift`: a highlighted bubble's time was drawn inside the bubble, over its text (F1). The overlay now holds a zero-width anchor on the bubble's outer edge, and the time hangs off its far side with the 8 pt gap.

   Layout only; checked again in the app by the manager, no unit test.
8. **A time in the chat opens the live drawer at the live end** (`TranscriptUI/FollowController.swift`, F14; live_transcript code that the chat's chips rely on). Cause, found by reading the code: the drawer opens for the chip, and while its list lays out it asks for the newest item (the appearance settle and `itemsChanged`); the reveal then stops following and asks for the cited item. The scroll to the newest can land before or after the reveal's; reaching the bottom while not following resumed following, which took the list back to the live end, where the highlighted bubble is out of view. `reveal(time:latest:)` now holds the reveal for `appearanceSettle` (1 s): with find closed, reaching the bottom in that time does not resume following, and the list asks for the revealed item again (when no request is pending), so it ends there in either order. Each case logs "The transcript stays at a revealed time: …", with whether the list had landed away from the bottom since the reveal and whether it scrolls to the revealed item again or a scroll is still pending. Return to live ends the hold at once. With find open, a bottom landing inside that second is left to find. The same path serves a note's time; the rule and its two limits (an item in the last screenful stays reading back at the bottom; a reader who scrolls to the bottom within that second is pulled back to the revealed item until the second ends) are in `components/chat_ui.md`, "Transcript highlight".
9. **A reveal that lands away from its item scrolls to it again** (`TranscriptUI/RevealLandingCheck.swift`, `FollowController`, `VisibleRowTracker`, `TranscriptBubbleList`; F14 in the original failure's conditions). Cause, from the hardware log and the code: the hold of step 8 never ran (no "revealed time" line at 17:08), so the list never reached the bottom; the reveal's own scroll landed in the wrong place. The transcript `List` makes its rows lazily and estimates the heights of rows it has not made (its content height was about 55,000 pt nine minutes into the recording), so a scroll to an item far from what is in view lands short of it or past it: the 1:03 chip landed at about 2:30–4:00. Now, 200 ms after the list performs a scroll to a revealed item, it checks the item's row against what the reader sees (`VisibleRowTracker.placement(of:)`, from the frames the rows report, between the top inset and the container height less the bottom inset; `ScrollSample.insetBottom` comes from `contentInsets.bottom`, which on the meeting page covers the pinned band and, with the card open, the card). Out of view (above, below, or not made), the follower asks for the item again, at most three times; in view, the check ends. A check made while the scroll to the item still waits uses no attempt; a scroll to another item pending, an explicit scroll (a find match) and Return to live end the check. Every check logs where the reveal landed against its time, with the view's height and insets: "The reveal of 63.0 s landed in view, at 58.2–92.4 s (view 431 pt, insets 0 top, 0 bottom)", or "… landed at …, the item notShown; scrolling to it again (attempt 1 of 3)", or "… after 3 more scrolls; leaving it there", or "… gave way to a scroll to another item". It runs for a reveal in the saved Transcript tab too. The held-landing log of step 8 now writes the first held landing and those that ask again, with a count, instead of one line per jitter (52 lines in 50 ms in the F14b run, with one request; the rest found a scroll pending).
10. **An empty transcript is no transcript to ask about** (`MeetingChat`, `TranscriptionService`, `AppCore+Chat`). A pass over silence saves a transcript with no text ("Meeting transcript was empty."), which made the band read "Ask about this meeting"; a question then failed with "There's no transcript to answer from yet." One rule for "has text", `ChatEvidence.hasText` (a segment whose text, on one line and trimmed, is not empty), now serves the evidence, the field (`MeetingChatService.hasTranscriptToAsk`, for `refreshTranscriptFlag` and the meeting page's load) and the save hook: `TranscriptionService.onTranscriptSaved` passes the saved segments' texts, and AppCore calls `transcriptWasSaved(meetingID:hasText:)` with `hasTranscriptText(_:)`. A save sets the flag either way, since it replaces the preferred transcript, and once a save has set a meeting's flag, readings leave it (a reading taken before the pass saved would be stale). So after Stop on a silent recording, or a Retry or re-transcription that comes back empty, the band reads "This meeting has no transcript to ask about".
11. **Row frames read against the list itself** (`TranscriptUI/VisibleRowTracker.swift`, `TranscriptBubbleList`; the landing check in the recording drawer). Every landing check in the drawer misread the list: "landed at no rows (view 431 pt, insets 0 top, 0 bottom), the item below", three retries, then "leaving it there", while the cited bubble was in view at the drawer's top (RECHECK2-landing-log.txt). Cause: the rows reported `frame(in: .scrollView)`, but a macOS `List` is not a SwiftUI `ScrollView`, so that space resolved to an outer one (the window). On the meeting page the list starts at the window's top, so the numbers matched the scroll geometry and the check passed; the drawer's list starts about 540 pt down the window, so every row's top was past the 431 pt view and read as below, and no row read as in view. Rows and the list now both report their frames in the window (`.global`), and the tracker reads each row against the list's top edge (`updateList(frame:)`), so y = 0 is the list's top in both places. The same frames feed `topVisibleStartTime`, the draft-to-final anchor: the drawer passes no anchor binding and has no header row (so it read nil anyway), and the meeting page's list starts at the window's top, so no live_transcript behaviour changed; `isHeaderVisible` reads the scroll offset, not row frames. The drawer's visual pass in the F14 re-check may have come from the wasted retries (each scroll to the item again), so it does not show that the first scroll lands right.
   - **An assumption the re-check verifies:** the tracker takes the list's layout frame to be its scroll view's, starting at the window's top under the 52 pt toolbar on the meeting page and spanning the bottom inset, so the content insets apply from the list's top. If SwiftUI lays the `List` out inside the safe area instead, the list's top is 52 in the window and the top inset counts twice: a row at the reader's top edge reads as above, the view's lower edge moves 52 pt into the card, and `topVisibleStartTime` picks the row below the true top one (shifting the draft-to-final anchor). The code cannot settle this; the meeting-page chip in the re-check does. The landing line now shows the list's frame in the window: "… (view 1290 pt, list at 0 pt in the window, 1290 pt high, insets 52 top, 1032 bottom)". "list at 0 pt" confirms the assumption; "list at 52 pt" (or a height of 1290 less the insets) means the measurement must read rows against `listTop - insetTop`, to be fixed then.
   - A follow-mode change (`onChange(of: follow)`) now passes the old tracker to the new `ListState`, which keeps the list's frame and header height; they only arrive when they change. No call site changes `follow` today.
